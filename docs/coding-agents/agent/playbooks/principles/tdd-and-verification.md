# TDD 和验证原则

默认使用 TDD，但允许按风险分层执行：

- 纯逻辑必须 TDD。
- bug 修复必须先写回归测试。
- 复杂业务流程先写验收测试或集成测试。
- UI 变化至少要有组件测试、截图验证或手动验证记录。
- 原型探索可以先 spike，但 spike 不能直接当最终实现；进入正式实现前要补测试。

推荐循环：

```text
需求 -> 最小测试 -> 失败 -> 最小实现 -> 通过 -> 重构 -> 完整验证
```

## 失败测试必须真的失败

RED 的合格标准：

```text
测试失败，并且失败信息能证明当前代码缺少目标行为。
```

不接受：

- 测试没跑就写实现。
- 测试因为语法错误失败，却当成 RED。
- 测试断言太弱，永远会通过。
- 先写实现再补测试。

## 完成前必须有新鲜验证证据

完成声明必须满足：

```text
Identify -> Run -> Read -> Verify -> Claim
```

也就是：

1. Identify：什么命令能证明任务完成？
2. Run：实际运行命令。
3. Read：读取完整输出和 exit code。
4. Verify：确认输出支持声明。
5. Claim：再说完成。

最终回复应该包含：

```text
已运行：
- ./scripts/test：通过
- ./scripts/check：通过

未运行：
- E2E：本任务不涉及浏览器路径
```

不能写：

```text
应该没问题
看起来可以
理论上通过
```
