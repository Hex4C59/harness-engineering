# 既有项目 `AGENTS.md` 模板

这个模板用于给已有仓库创建或补充根目录 `AGENTS.md`。

既有项目的 `AGENTS.md` 不应该重写项目百科，也不应该强行套用新项目目录结构。它的作用是让 agent 进入项目后知道：

- 先读哪里。
- 哪些事实已经确认，哪些仍然待确认。
- 常用命令和验证入口是什么。
- 哪些文件或操作默认不要碰。
- 什么情况下必须先停下来让用户确认。
- 完成任务前要交代哪些验证和风险。

使用方式：

1. 先用只读审计找证据，不要让 agent 猜测项目事实。
2. 能从仓库确认的信息写入模板。
3. 不能确认的信息保留 `待确认`，并列给用户决定。
4. 如果已有 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`、`.github/copilot-instructions.md` 或贡献指南，只做增量合并，不要复制出互相冲突的规则。

```md
# AGENTS.md

这个项目是一个既有项目。修改前先尊重已有结构和约定，不要按新项目模板重排目录。

本文件是 agent 入口地图和硬约定，不是项目百科。缺失或不确定的信息必须标注为 `待确认`，不要编造。

## 项目上下文

| 项目事实 | 当前信息 | 证据来源 |
|---|---|---|
| 项目类型 | 待确认 | 待确认 |
| 技术栈 | 待确认 | 待确认 |
| 包管理器 / 构建工具 | 待确认 | 待确认 |
| 主要源码目录 | 待确认 | 待确认 |
| 主要测试目录 | 待确认 | 待确认 |
| 主要运行入口 | 待确认 | 待确认 |
| CI / 发布入口 | 待确认 | 待确认 |

填写规则：

- 只写能从 `README.md`、包管理文件、构建文件、CI 配置、现有 docs 或源码结构确认的信息。
- 如果多个来源冲突，保留冲突说明，不要自行裁决为事实。
- 如果项目没有某类文件，不要创建虚假的入口；在 `docs/project-status.md` 或本文件中标注待补。

## 必读入口

按任务相关性渐进读取，不要一次性读取整个仓库。

1. `README.md`：项目目标、安装和运行方式。
2. `CONTRIBUTING.md`：贡献流程和代码约定，如存在。
3. `docs/README.md`：项目文档地图，如存在。
4. `docs/project-status.md`：当前状态、验证命令、未决问题，如存在。
5. `docs/development.md`：本地开发命令，如存在。
6. `docs/testing.md`：测试策略、TDD 和 bug 修复流程，如存在。
7. `.github/workflows/` 或其他 CI 配置：验证、构建、发布流程，如存在。
8. 包管理和构建文件：例如 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`Makefile`、`justfile`。
9. 与当前任务相关的源码、测试、配置和文档。

如果上述文件不存在，不要假设其内容；先通过只读审计确认替代入口。

## 常用命令

优先沿用项目已有命令。不要为了统一格式而替换成熟项目的既有工具链。

| 任务 | 命令 | 状态 | 证据来源 |
|---|---|---|---|
| 安装依赖 | 待确认 | unknown | 待确认 |
| 启动开发环境 | 待确认 | unknown | 待确认 |
| 运行测试 | 待确认 | unknown | 待确认 |
| 运行单个测试 | 待确认 | unknown | 待确认 |
| lint | 待确认 | unknown | 待确认 |
| typecheck | 待确认 | unknown | 待确认 |
| build | 待确认 | unknown | 待确认 |
| 完整验证 | `./scripts/check` 或待确认 | unknown | 待确认 |

命令状态说明：

- `confirmed`：已从仓库文件确认，并至少成功运行过一次。
- `documented`：文档或配置中存在，但本地尚未运行确认。
- `blocked`：命令存在，但因环境、依赖、凭据或外部服务暂不可运行。
- `unknown`：尚未找到可靠来源。

如果没有统一验证入口，优先新增或建议新增 `scripts/check`，用于包装已有 format / lint / typecheck / test / build 命令。不要伪造成功结果。

## 工作规则

- 修改前先阅读相关文档和现有代码，不要猜测项目结构。
- 保持既有风格、命名、目录结构和测试方式。
- 不做无关重构、改名、格式化、依赖升级或目录重排。
- 非平凡任务先写或更新 `docs/plans/` 下的计划，并等待确认。
- Bug 修复先复现，再写失败回归测试，再做最小修复。
- 如果已有测试方式，优先沿用；不要为了 TDD 重写测试框架。
- 如果需求、验收标准或影响范围不清楚，先暂停并列出问题。
- 不删除或覆盖已有资料，除非用户明确要求。
- 发现文档和代码冲突时，以代码和可运行验证为准，并记录文档待更新。

## 修改边界

默认不要修改：

- 生成物、缓存、构建产物。
- `vendor/`、第三方源码、自动生成代码。
- lockfile，除非当前任务明确涉及依赖变化。
- 数据库 migration、schema、seed 数据，除非当前任务明确需要。
- 生产配置、部署脚本、CI/CD workflow。
- secret、token、私钥、真实生产数据、本机个人路径。
- 大型格式化结果或全仓库重排。

如果当前任务必须修改上述内容，先说明原因、风险、验证方式和回滚方式。

## 高风险改动

遇到以下情况先停下来确认，不要直接执行：

- 新增、删除或升级依赖。
- 更换框架、构建工具、测试框架、包管理器。
- 修改模块边界、目录结构或公共 API。
- 修改认证、授权、加密、安全策略。
- 修改数据库 schema、migration 或数据迁移逻辑。
- 修改部署、CI/CD、生产配置或发布流程。
- 执行删除、覆盖、批量移动、批量格式化等高影响操作。
- 访问外部服务、生产环境、真实用户数据或私有凭据。

## 任务流程

### 小修

1. 读取相关文件。
2. 做最小修改。
3. 运行局部验证。
4. 检查 diff 是否只包含本任务内容。

### 新功能

1. 确认需求、非目标和验收标准。
2. 必要时写 Spec 或 Execution Plan。
3. 拆成 reviewable slices。
4. 优先写失败测试。
5. 实现当前 slice。
6. 运行相关验证。
7. 更新状态文档或计划。

### Bug 修复

1. 复现问题。
2. 找到根因，不做猜测式修复。
3. 写失败回归测试，或说明为什么无法自动化。
4. 做最小修复。
5. 运行回归测试和相关验证。

### 重构

1. 先确认行为测试保护。
2. 小步修改，每步可验证。
3. 不混入功能变化。
4. 保持 diff 可 review、可回滚。

### 文档

1. 更新与当前事实直接相关的文档。
2. 检查链接、目录和命令是否仍然有效。
3. 对不确定信息标注 `待确认`。

## 验证规则

- 完成前必须运行与本轮改动相关的最小验证命令。
- 有统一入口时优先运行 `./scripts/check`。
- 如果完整验证不可运行，说明原因，并运行可用的最小替代命令。
- 不允许在没有新验证结果时说“完成”“修好了”“测试通过”。
- 需要在最终回复中列出实际运行的命令、结果和未验证项。

## 完成标准

一次任务完成前必须确认：

- 已说明改了什么、为什么这样改。
- 已运行相关验证命令，并读取完整输出和 exit code。
- 已检查 `git status` 或等价文件列表。
- 已检查 diff，确认没有无关改动、生成产物、secret 或本机路径。
- 必要文档、计划或状态文件已更新。
- 剩余风险、未验证项和下一步已列出。

## 不确定信息处理

如果信息无法从仓库确认：

1. 保留 `待确认`。
2. 写明已经检查过哪些位置。
3. 给出需要用户确认的问题。
4. 不要为了让文档完整而编造命令、目录、架构或测试策略。
```
