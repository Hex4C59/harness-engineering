# 什么是 Harness Engineering

## 核心定义

在 AI agent 语境里，**harness** 是模型之外的一整套运行系统：它决定 agent 能看到什么、能调用什么工具、如何保存状态、如何验证结果、何时继续、何时停下、如何把失败反馈成下一次更可靠的行为。

可以用一个公式理解：

```text
Agent = Model + Harness
```

模型提供推理、语言、规划和生成能力；harness 把这些能力接到真实环境里，并用规则、工具、状态和反馈把它变成能完成工作的 agent。

## 它和提示词工程的区别

提示词工程主要改变一次交互里的指令表达。Harness engineering 改变的是 agent 每次工作所处的系统。

| 维度 | 提示词工程 | Harness engineering |
|---|---|---|
| 关注点 | 怎么说清楚任务 | 怎么搭建 agent 可持续工作的环境 |
| 作用范围 | 单次对话或单个 prompt | 整个仓库、运行时、工具链和反馈闭环 |
| 失败处理 | 改提示词、补说明 | 把失败转成文档、工具、检查、权限或流程改进 |
| 可验证性 | 依赖模型自觉 | 通过测试、lint、日志、评审、trace、状态记录验证 |
| 可复用性 | 容易散落在聊天里 | 版本化在仓库、脚本、CI、配置和状态文件中 |

## 它和上下文工程的区别

上下文工程关注“给模型什么信息”。Harness engineering 更大一层，除了上下文，还包括：

- 工具：shell、文件编辑、浏览器、数据库、MCP、业务 API。
- 状态：任务计划、进度、会话、决策记录、运行日志。
- 权限：哪些路径可读写、哪些操作要审批、哪些工具不能用。
- 验证：测试、类型检查、lint、UI 验证、trace 查询、回归检查。
- 生命周期：任务如何开始、暂停、恢复、分叉、归档。
- 反馈闭环：失败如何被分类、记录、修复并变成新约束。

上下文是 harness 的一部分，但 harness 不止是上下文。

## 它和 agent framework / runtime 的区别

这些词边界还在演化，但可以先这样区分：

| 概念 | 大致含义 |
|---|---|
| Framework | 帮你搭 agent 的库或抽象，如工具调用循环、节点图、多 agent 编排 API |
| Runtime | 负责 agent 实际运行的执行环境，如进程、线程、事件流、sandbox、持久化 |
| Harness | 围绕模型和 runtime 的完整控制系统，包含上下文、工具、权限、状态、验证和反馈 |

一个 framework 可以帮你写 harness，一个 runtime 可以承载 harness，但 harness 是面向“让 agent 可靠交付任务”的系统设计。

## 一个典型 agent harness 由什么组成

### 1. Agent Loop

最核心的循环通常是：

```text
接收任务 -> 选择上下文 -> 调用模型 -> 执行工具 -> 观察结果 -> 决定继续或结束
```

这只是起点。真正的 harness 会在循环周围加状态、权限、验证和恢复。

### 2. Context Map

Agent 不应该一开始就读一大坨说明。更好的方式是：

- `AGENTS.md` 作为入口地图。
- `docs/` 作为可检索的事实来源。
- 当前状态、实施计划、架构说明、决策记录分开维护。
- 只把当下任务需要的信息递进式暴露给 agent。

这也是本仓库已经开始采用的方式。

### 3. Tool Surface

Harness 要定义 agent 能用哪些工具，以及每个工具的约束：

- 读写文件。
- 搜索代码。
- 运行测试。
- 启动本地服务。
- 操作浏览器。
- 查询日志、指标、trace。
- 调用业务 API。
- 创建 PR 或评论。

工具越强，越需要清晰权限和审计。

### 4. State And Memory

长任务不能只靠模型上下文窗口。Harness 需要把重要状态落到外部：

- 任务计划。
- 已完成步骤。
- 决策记录。
- 失败原因。
- 测试输出。
- 会话 ID。
- 变更摘要。

状态持久化让新 agent、新窗口、下一轮任务能接上，而不是重新猜。

### 5. Verification Loop

Agent 说“完成了”不等于真的完成了。Harness 要提供可执行验证：

- 单元测试。
- 集成测试。
- lint 和格式化。
- 类型检查。
- UI 截图或浏览器自动化。
- 日志/指标/trace 验证。
- 人工审批点。

验证结果要能回流给 agent，让它自己修。

### 6. Guardrails And Permissions

Harness 不是只给 agent 更多能力，也要限制能力：

- 文件系统读写范围。
- sandbox 或容器隔离。
- 网络访问策略。
- Secret 不进入 prompt 或日志。
- 高风险命令需要审批。
- 非授权 agent 不能越权操作。

越是让 agent 长时间运行，越需要这些边界。

### 7. Feedback And Garbage Collection

Agent 会复制仓库里的坏模式，也会制造漂移。Harness 要定期清理：

- 把重复失败写成新规则。
- 把人工评论沉淀成文档或 lint。
- 把临时脚本升级成稳定工具，或删除。
- 定期检查过期文档。
- 跟踪技术债。

这一步让 agent 的产出不会随着速度增加而失控。

## 最短心智模型

如果 agent 失败了，不要只问：

```text
我该怎么写一个更好的 prompt？
```

更应该问：

```text
这个失败暴露了 harness 缺少什么？

- 缺上下文？
- 缺工具？
- 缺权限边界？
- 缺测试？
- 缺状态记录？
- 缺日志可见性？
- 缺清晰的停止条件？
- 缺决策记录？
```

把答案沉淀进仓库、工具或流程，就是 harness engineering。
