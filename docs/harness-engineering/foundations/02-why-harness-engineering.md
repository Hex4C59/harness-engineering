# 为什么要用 Harness Engineering

## 1. 因为模型能力不等于交付能力

强模型可以写代码、解释错误、生成计划，但真实项目交付需要更多东西：

- 找到正确上下文。
- 理解项目边界。
- 修改正确文件。
- 跑正确验证。
- 处理失败。
- 不破坏既有约定。
- 在新窗口或新任务中保持连续性。

这些能力很多不在模型本体里，而在模型外面的 harness 里。

## 2. 因为人类注意力会先成为瓶颈

Agent 可以并行、长时间、低成本地产出变更。问题会从“谁写代码”变成：

- 谁定义任务？
- 谁判断完成？
- 谁维护架构一致性？
- 谁防止质量漂移？
- 谁把失败变成下次不会再犯的机制？

如果没有 harness，人会被迫不停复制上下文、审查低级错误、解释同样规则。Harness 的价值就是减少这种重复注意力消耗。

## 3. 因为聊天记录不是系统事实来源

聊天窗口里的信息对下一次 agent 运行通常不可见，也难以验证。可靠的 agent 项目需要把关键知识放到仓库里：

- 架构文档。
- 实施计划。
- 当前状态。
- 任务验收标准。
- 设计决策。
- 编码规则。
- 运行命令。
- 常见失败和恢复方法。

这也是为什么 `AGENTS.md` 不应该变成百科全书。它更适合作为入口地图，把 agent 指向更细的事实来源。

## 4. 因为高吞吐会放大架构漂移

人类开发慢，所以坏模式扩散也慢。Agent 开发快，坏模式也会复制得更快。

常见漂移包括：

- 同一逻辑被重复实现。
- 模块边界被绕过。
- 文档和代码不一致。
- 临时脚本长期留存。
- 测试只覆盖 happy path。
- 错误处理风格越来越散。
- 权限和 secret 边界被逐步侵蚀。

Harness 要把“好品味”变成可执行规则，而不只是一段建议。

## 5. 因为长任务需要外部状态

模型上下文窗口有限。长任务跨越多个小时、多个窗口、多个 agent 时，必须有外部状态承接：

- 文件系统保存中间结果。
- Git 保存变更历史。
- 计划文档保存进度。
- 日志保存运行证据。
- 测试保存可复现反馈。
- 决策记录保存为什么这样做。

没有这些，agent 会反复失忆、重复探索、误解历史。

## 6. 因为可靠性来自反馈闭环

一次成功不能说明 harness 好。真正重要的是失败后系统如何变化。

低质量反馈：

```text
这次你做错了，下次注意。
```

高质量反馈：

```text
失败原因：agent 修改了不该修改的用户文件。
Harness 改进：
- 在 AGENTS.md 增加不要覆盖用户变更的规则。
- 在写入前检查 git diff。
- 对危险命令要求人工确认。
- 把该案例加入测试或检查清单。
```

Harness engineering 的核心就是让反馈可复用、可执行、可审计。

## 7. 因为它适合 noclaw 这类项目

Noclaw 本身要实现一个轻量 agent 编排系统：通道、SQLite、组队列、容器、IPC、调度器、安全隔离。这些正是 harness 的典型组成部分。

如果只把 noclaw 看成“调用 Claude 的机器人”，它会很容易变成一堆通道适配器和提示词。

如果把 noclaw 看成“agent harness”，设计重点会更清晰：

- 通道是输入/输出面。
- SQLite 是事实来源和外部记忆。
- 组目录是上下文和权限边界。
- 容器是 sandbox。
- IPC 是工具回调层。
- Scheduler 是长期任务入口。
- Logs 是可观测性。
- Tests 是验证闭环。
- `AGENTS.md` 和 `docs/` 是 agent 可读知识库。

这个视角能帮助项目早期就避免大而散。
